韌體與嵌入式：程式怎麼摸到硬體

韌體的每件事都在回答同一組問題：上電後先跑誰？怎麼確定要跑的東西是對的？改一個暫存器會不會踩到別人？硬體有事時誰先知道、誰去處理？答錯其中一題，結果就是變磚、偶發錯誤或當機後沒人救。

對應 taxonomy K01～K05。難度標籤：L1是什麼　L2為什麼　L3出問題怎麼辦。

K01Firmware 架構與 Bootloader

一句話：Bootloader 是上電後第一段跑的程式，負責決定跑哪個 image、確認它沒壞沒被改、再把控制權交出去；更新韌體的安全性幾乎全靠它的設計。

L1是什麼

名詞意思
Bootloader上電後先跑的小程式：檢查有沒有新版、驗證 App、跳過去。分兩種：晶片廠燒死在 ROM 裡的（ROM bootloader，不能改），和自己寫、放在 Flash 開頭的（secondary bootloader）。ROM bootloader 的燒錄用法見 ISP 燒錄
Reset vector／vector tableCortex-M 上電後從位址 0x0000_0000 讀第一個 word 當堆疊指標（MSP）、第二個 word 當 Reset_Handler 位址，後面接 NMI、HardFault…各中斷的進入點。這張表叫 vector table
VTORVector Table Offset Register：告訴 CPU 中斷向量表在哪。Bootloader 跳 App 前要把它改成 App 的起點
Startup codemain() 之前跑的程式：把 .data 初值從 Flash 複製到 RAM、把 .bss 清成 0、設時脈，然後才呼叫 main()
Image layoutimage 的格式：header（magic、版本、長度、載入位址）＋ 程式本體 ＋ 檢查碼（CRC、hash、簽章）＋ 狀態旗標（見上圖）
Linker script／memory map規定每一段程式放在哪個位址。有 bootloader 時，App 必須連結到 bootloader 之後的位址，不能再從 Flash 起點開始
OTA／DFUOver-The-Air 無線更新／Device Firmware Upgrade（USB 等有線更新）。都是「在現場換韌體」
單 bank／雙 bank（A/B）單 bank：只有一塊 App 區，更新要先擦掉舊版。雙 bank（A/B slot）：新版寫進另一塊，驗證過才切換，舊版留著當退路
Test／Confirm（試跑／確認）新版先只准跑一次，App 自我檢查通過後寫「已確認」旗標才算數；沒確認就重開，bootloader 會回退舊版
Secure boot／chain of trust每一級驗證下一級才交棒：ROM 驗 bootloader、bootloader 驗 App。信任的起點（root of trust）是不能改的 ROM 程式，加上燒在 OTP／eFuse 裡的公鑰 hash
Anti-rollback版本計數器存在 OTP（只能往上加），bootloader 拒絕跑版本比計數器低的 image，防止被刷回有漏洞的舊版

L2為什麼

  • 為什麼 bootloader 要獨立一塊、而且盡量不更新？它是唯一能救回 App 的東西。更新 App 時 bootloader 不動，最壞也只是 App 壞掉、停在 bootloader 等重燒；連 bootloader 都換，中途斷電就沒有任何東西能接手。
  • CRC 跟簽章差在哪？CRC 只防「意外」：傳輸錯、寫一半、Flash 位元翻轉。任何人都能對竄改過的 image 重算 CRC，所以防不了惡意修改。簽章要用私鑰才產得出來，裝置只存公鑰（或它的 hash），才能確認「這是原廠出的」。
  • 為什麼更新一定要「先寫、再驗、最後才切換」？切換那一步要是不可分割的：改一個旗標或一個指標。前面寫多久、斷幾次電都沒關係，因為在切換之前，bootloader 看到的永遠是一個完整的舊版。
  • CRC 都對了，為什麼還要試跑＋確認？CRC 只證明「內容跟 build 出來的一樣」，不證明程式能跑。新版可能在這塊板子的硬體版本上一初始化就當。配合 watchdog：新版卡死就 reset，bootloader 看到「試過但沒確認」就回退。
  • 為什麼跳 App 前要先清場？bootloader 開過的中斷、SysTick、DMA 還在動。App 還沒設好自己的向量表就有中斷進來，CPU 會跳進 bootloader 的 handler 或空位址，直接 HardFault。所以要關中斷、停 SysTick、清 NVIC pending、改 VTOR、設 MSP，最後才跳。
  • 單 bank 為什麼要從 RAM 執行燒錄程式？多數 Flash 在擦寫時，同一個 bank 不能同時讀指令，CPU 會被卡住（stall）。所以寫 Flash 的程式（連同期間會用到的 ISR）要先搬到 RAM 跑；雙 bank 的 MCU 則可以邊跑 A 邊寫 B。
  • 跟顯示驅動 IC 的關係？TCON、driver IC 的參數（gamma、VCOM、時序）常寫在 OTP／MTP，或透過 I²C 從外部 Flash 載入。寫 C# 燒錄工具時，同樣要做到「寫完讀回比對、寫入旗標放最後、斷線能重來」，邏輯跟 bootloader 一樣。

L3出問題怎麼辦

現象最可能原因對策
Bootloader 跳到 App 後馬上 HardFault，或一有中斷就當VTOR 沒改到 App 起點、App 的 linker script 還從 Flash 起點連結、bootloader 開的中斷或 SysTick 沒關跳之前關中斷、停 SysTick、清 NVIC pending；設 VTOR 與 MSP；確認 App linker script 的 FLASH 起點等於 slot 位址
OTA 更新到一半斷電，裝置開不了機單 bank 直接覆寫、沒有回退；或連 bootloader 都在這次更新裡改改雙 bank＋驗證後才切換；bootloader 不跟 App 一起更新；保留 ROM ISP 或 SWD 當最後救援（見 ISP）
新版 CRC 正確，但一開機就當，一直重開（boot loop）新版跟某版硬體不相容，或初始化卡住；沒有試跑／確認機制試跑一次＋App 確認旗標＋watchdog；bootloader 記錄重開次數，超過門檻就回退
產線燒錄後少數板子 CRC 驗證失敗寫 Flash 時電源跌落（Flash 寫入需要最低電壓，電池或電源夾具不穩）、沒等 busy 旗標就寫下一筆、燒錄後沒讀回比對開 BOR（欠壓重置），或用 PVD（電壓監測中斷）提早停寫；每塊等 busy 結束；燒錄程序加讀回比對
Bootloader 判定 image 無效，但用燒錄器直接燒同一個檔可以跑CRC 計算範圍或 padding（0xFF）跟 bootloader 不一致、header 長度或 endianness 寫錯、image 沒經過簽章步驟在 build 後處理（post-build）用同一支工具算 CRC 與簽章，不要手動拼檔；比對 header 欄位
有人把裝置刷回有漏洞的舊版bootloader 只驗簽章不看版本（舊版也是原廠簽的）加 anti-rollback：版本計數器放 OTP，新版確認後才往上加

K02Register 操作與 MMIO

一句話：週邊的暫存器就是某個記憶體位址，讀寫它就是在控制硬體；難處在於只改你要的那幾個 bit，而且編譯器、中斷、硬體本身都可能在你背後動它。

L1是什麼

名詞意思
MMIOMemory-Mapped I/O：週邊暫存器映射到記憶體位址，CPU 用一般的 load／store 指令讀寫。Cortex-M 的週邊大多從 0x4000_0000 開始
Register map規格書裡的暫存器表：每個暫存器的 offset、名稱、每個 bit field 的意思、存取型別、reset 值。實際位址＝週邊 base address＋offset
Bit field／mask／shift一個暫存器切成好幾段欄位。mask 標出欄位佔哪幾個 bit，shift 是欄位最低位的位置
Read-modify-write（RMW）讀出整個暫存器、只改某幾個 bit、再寫回。|=、&= 都是 RMW
volatile告訴編譯器「這個值隨時可能被外部改掉」，每次存取都要真的去讀寫，不准快取在 CPU 暫存器、不准省略
存取型別RW 可讀寫；RO 唯讀（狀態）；WO 唯寫（讀回來沒意義）；W1C 寫 1 清除、寫 0 無效（中斷旗標）；W1S 寫 1 設定；RC 讀了就清除；Reserved 保留位元
Set／clear 專用暫存器例如 STM32 GPIO 的 BSRR：寫 1 到低 16 bit 讓腳位變高、寫 1 到高 16 bit 讓腳位變低，一次寫入完成，不用先讀
Bit-bandingCortex-M3／M4 的選配功能：把某段 SRAM 與週邊的每一個 bit 對應到另一段別名位址的一個 word，寫那個 word 就是不可分割地改那一個 bit。Cortex-M0 沒有
Shadow／preload 暫存器軟體寫的是「預備」那一份，硬體在特定時機（例如 Timer 的 update event）才複製到「生效」那一份，避免改到一半的值被用到

L2為什麼

  • 沒有 volatile 會怎樣？編譯器只看得到你的程式。while (!(UART->SR & RXNE)); 在它眼裡迴圈內沒人改 SR，於是讀一次就當常數，開 -O2 後變成死迴圈。ISR 與主程式共用的旗標變數也一樣。
  • volatile 不保證什麼？它只保證「每次都真的存取」，不保證不可分割（32 位元 MCU 上的 64 位元變數會分兩次讀，中間可能被 ISR 改）、不保證多核心之間的順序、也不處理 cache。要不可分割就靠關中斷、atomic 指令或鎖；順序靠記憶體屏障（例如 Cortex-M 的 DSB）。
  • RMW 為什麼會出 race？讀、改、寫至少三道指令（見上圖）。主程式與 ISR 改同一個暫存器的不同 bit，ISR 剛好插在中間，它的修改就被主程式手上的舊值蓋掉。這就是為什麼硬體要提供 BSRR、bit-band 這類一次寫完的機制。
  • W1C 旗標為什麼不能用 |= 清？SR |= FLAG_A 會先讀出 SR，如果 FLAG_B 剛好也是 1，寫回時 FLAG_B 也被寫了 1，等於一起清掉，B 中斷就不見了。W1C 寫 0 本來就無效，所以直接 SR = FLAG_A; 就好。
  • Reserved bit 為什麼要小心？規格書通常要求保留原值或寫 reset 值。新版晶片可能拿這個 bit 做新功能，亂寫可能誤開功能；用 RMW 改其他欄位剛好能保留它。
  • 為什麼要 shadow 暫存器？PWM 週期改到一半就生效，當下那個週期會長得很奇怪（glitch）。先寫預備值、等這個週期結束（update event）才換，輸出就是乾淨的。顯示 IC 的時序類暫存器常有類似的「寫入後在 frame 邊界才生效」設計，細節以各家規格書為準。
  • C# 工具寫 IC 暫存器時也一樣？是。透過 I²C／USB 改一顆 IC 的某個欄位，要先讀回整個 byte／word、用 mask 改、再寫回；碰到 W1C 欄位不能讀回再寫。把 register map 做成資料表（名稱、offset、mask、存取型別）讓程式自動套用，就不會每次手算。

L3出問題怎麼辦

現象最可能原因對策
Debug 版正常，開最佳化後輪詢迴圈卡死，或 ISR 設的旗標主程式看不到暫存器指標或共用變數沒加 volatile，讀取被提到迴圈外暫存器用 volatile 指標（廠商的 CMSIS 標頭檔已經做好）；共用旗標加 volatile，多 byte 的再加臨界區
某個設定 bit 偶發被改回原狀，很難重現主程式與 ISR（或兩個 RTOS task）對同一個暫存器做 RMWRMW 前後關中斷；改用 BSRR 這類 set／clear 暫存器或 bit-band；或規定只有一個模組能改這個暫存器
清了一個中斷旗標，另一個中斷從此不再觸發W1C 暫存器用了 |=，把其他剛好為 1 的旗標一起清掉W1C 直接寫要清的那個 bit：SR = FLAG_A;
用除錯器看暫存器之後，程式就收不到資料或旗標自己消失該暫存器是 read-to-clear（例如讀資料暫存器會清掉 RX 旗標），除錯器的 watch 視窗讀了一次不要在 watch 視窗放 RC 暫存器；程式裡讀一次存到變數再看
寫了暫存器卻完全沒反應，讀回來是 0週邊時脈沒開（clock enable 沒設）、暫存器被寫保護（要先寫 unlock key）、寫到唯讀位元先開週邊時脈；照規格書的解鎖順序；對照 register map 的存取型別
用 C 的 struct bit-field 寫暫存器，結果 bus fault 或改錯位置編譯器產生 8／16 bit 存取，但週邊只接受 32 bit 存取；bit-field 的排列順序由編譯器決定用 mask／shift 對整個 32-bit 暫存器操作，不用 C bit-field 描述硬體

K03Interrupt／Polling／DMA

一句話：Polling 是 CPU 自己一直去問，Interrupt 是硬體來叫 CPU，DMA 是交給專門的硬體搬、搬完叫一次。下面先整理 ISR 設計與常見故障，接著是 三種做法的互動模擬與成本比較。

L1是什麼

名詞意思
ISRInterrupt Service Routine：中斷發生時 CPU 跳去執行的函式
NVICCortex-M 的中斷控制器：管每個中斷的開關、待處理（pending）與優先權，支援巢狀（高優先權打斷低優先權）
優先權數字Cortex-M 上數字越小越優先，0 最高
中斷延遲從中斷發生到 ISR 第一道指令的時間。Cortex-M3／M4 固定 12 個 cycle（不含 FPU 存檔）；tail-chaining（一個 ISR 結束時下一個已在等，省掉出入堆疊）只要 6 個 cycle
臨界區暫時關中斷（或用 BASEPRI 只擋某優先權以下）保護共用資料的一小段程式
DMA專門搬資料的硬體，CPU 設好來源、目的、長度就去做別的事，搬完發一次完成中斷（詳見下方 DMA 段）

L2為什麼

  • ISR 為什麼要短？ISR 執行時，同等級與更低優先權的中斷都在排隊。ISR 裡做浮點運算、printf、等待 I²C，會讓別的中斷延遲甚至遺失（UART 的 FIFO 滿了就丟資料）。標準做法：ISR 只搬資料、清旗標、設一個 flag 或送訊息給 task，重活交給主迴圈或 task 做。Linux 的 top half／bottom half、threaded IRQ 是同一個想法。
  • 什麼時候用哪一種？開機初始化、等很短的狀態用 polling；不定時、要即時反應的事件（按鍵、少量資料）用 interrupt；大量連續資料（SPI 送畫面、ADC 連續取樣、UART 長封包）用 DMA。只搬幾個 byte 時 DMA 的設定成本反而比較貴。
  • 用 RTOS 時優先權有什麼限制？以 FreeRTOS 為例，會呼叫 ...FromISR() API 的 ISR，優先權數字必須 ≥ configMAX_SYSCALL_INTERRUPT_PRIORITY（邏輯上比較不急）。比它更急的 ISR 不能呼叫 RTOS API。中斷預設優先權是 0（最高），所以一定不合法，要記得改。

L3出問題怎麼辦

現象最可能原因對策
UART 偶發 overrun、掉 byte其他 ISR 太長或臨界區關中斷太久，UART 中斷進不來縮短 ISR、調高 UART 優先權、改用 DMA＋環形緩衝
同一個中斷一直重複進入，主程式跑不動ISR 沒清旗標；或在 ISR 最後一行才清，寫入還在匯流排上就返回，硬體旗標還沒放下又觸發一次確實清旗標，並在 ISR 前段清；清完讀回一次或加 DSB 確保寫入完成
開 FreeRTOS 後一進某個 ISR 就停在 configASSERT該 ISR 優先權太高（數字太小，例如預設 0），卻呼叫了 FromISR API把優先權數字設成 ≥ configMAX_SYSCALL_INTERRUPT_PRIORITY
主程式讀到的計數值偶爾錯得離譜ISR 更新的多 byte 變數（例如 32 位元 MCU 上的 64 位元時間戳）被讀到一半讀取時關中斷，或讀兩次比對一致才用
Cortex-M7 用 DMA 收資料，CPU 讀到舊值D-Cache 沒同步收完先 invalidate cache，或 buffer 放 non-cacheable 區（見 DMA 三個限制第 3 點）

K03DMA：誰來搬資料

DMA 是 CPU 雇來的搬運工。
CPU 負責動腦，DMA 負責搬，搬完再回報一聲。

MCU 常常要把資料從 A 搬到 B，例如 UART 收到的字元要放進 RAM。沒有 DMA 的話只能靠 CPU 一個 byte 一個 byte 地搬。搬資料不用動腦，但 CPU 在搬的時候就不能做別的事。

DMA 是 MCU 裡一塊專門搬資料的小硬體。CPU 交代它三件事之後就可以去忙別的：從哪裡搬、搬到哪裡、搬多少。

成本怎麼算：Polling 要一直等到最後一個 byte 進來；Interrupt 每個 byte 都要付一次中斷進出加搬移（20）；DMA 不管搬幾個 byte，都只付設定（70）加完成中斷（20）這筆固定成本。

K03什麼時候用哪一種

K03三個要知道的限制

1. DMA 跟 CPU 共用同一條 bus

DMA 在搬的時候，CPU 如果也要存取記憶體，兩邊得排隊輪流用。所以 CPU 還是會受到影響，只是影響小很多。

2. 還沒搬完的 buffer 不能拿來用

DMA 在背景搬資料，CPU 必須等到完成通知才能讀，不然會讀到一半新、一半舊的資料。常見解法是 double buffer（雙緩衝）：DMA 寫 A 的時候 CPU 處理 B，下一輪兩邊對調。MCU 通常有 half-transfer 中斷可以配合這種做法。

3. 有 cache 的 MCU 要處理 cache 一致性

像 Cortex-M7 這種有 D-Cache 的晶片，DMA 是直接寫進 RAM，CPU 讀到的卻可能是 cache 裡的舊值。DMA 收完資料後要先 invalidate（讓 cache 失效），CPU 要交給 DMA 送出去的資料要先 clean（寫回 RAM）。另一種做法是把 buffer 放在 non-cacheable 區域。

K04週邊控制

一句話：GPIO 決定腳位怎麼推、空著時落在哪；Timer 是可設定的計數器，PWM 和輸入量測都靠它；Watchdog 是沒人按時餵就把系統重開的保險。

L1是什麼

名詞意思
GPIO 模式輸入（浮接／上拉／下拉）、輸出（push-pull／open-drain）、alternate function（交給 UART、SPI 等週邊）、analog（給 ADC，也是最省電的閒置狀態）
Push-pull／open-drain見上圖。I²C、多顆共用的中斷線、要轉電壓時用 open-drain
Pull-up／pull-down沒人驅動時把腳位拉到確定的高或低。MCU 內建的通常是弱上拉，例如 STM32 約 40 kΩ（25～60 kΩ）；要快或要準就外接

L2為什麼

  • 為什麼沒用到的腳不能浮接？浮接的輸入會隨雜訊在高低之間晃，輸入端的 Schmitt trigger 一直翻轉就會耗電，還可能誤觸中斷。省電做法是設成 analog 模式；要當數位輸入就加上拉或下拉。
  • 上拉電阻也會耗電？腳位被拉低時，上拉電阻上一直有電流：3.3 V ÷ 40 kΩ 約 82 µA。電池產品待機時要檢查每個「被拉低的上拉腳」。
  • PWM 頻率和解析度為什麼互相拉扯？Timer 時脈固定時，頻率越高 ARR 就越小，能調的 duty 階數就越少：72 MHz 時脈、1 kHz PWM 可以有 72000 階；調到 1 MHz 只剩 72 階。背光調光要細緻就不能把頻率拉太高；太低又可能被看到閃爍，落在可聽頻段還可能讓電感、電容發出嘯叫。
  • 改 PWM duty 為什麼要開 preload？沒開時新值立刻生效，若新的 CCR 比計數器目前的值還小，這個週期就錯過比較點，輸出一個整週期的高或低（glitch）。開 preload 後新值在 update event 才生效（見 K02 的 shadow 暫存器）。
  • 餵狗要放在哪？放在「確認系統健康」之後，通常是主迴圈或監控 task 收齊各 task 的存活回報才餵。放在 timer ISR 裡最糟：主程式死了，timer 中斷照跑照餵，watchdog 永遠不會出手。
  • 為什麼還需要視窗看門狗？程式跑飛時可能剛好卡在一個一直餵狗的小迴圈裡。WWDG 規定只能在視窗內餵，餵太快也 reset，能抓到這種「看起來活著其實壞了」的狀態。
  • 跟顯示驅動 IC 的關係？系統端常用 GPIO 控制 driver IC 的 RESET、待機腳，用 PWM 調背光。RESET 腳要先確認是低有效還是高有效、上電時的預設電位（內部上拉或下拉），否則 MCU 還在開機時 IC 就被誤放開 reset。

K05Driver 與 OS 整合

一句話：有作業系統時，只有 kernel 能直接碰硬體；驅動分成「懂這顆控制器」和「懂這顆 IC」兩層，硬體長怎樣則寫在裝置樹，不寫死在程式裡。

L1是什麼

名詞意思
Kernel space／user space兩個隔離的記憶體與權限區。kernel（含驅動）權限最高、能碰硬體；一般程式在 user space，只能透過 system call 請 kernel 代辦
System calluser 進 kernel 的唯一正門：open、read、write、ioctl、mmap 等
/dev、ioctl、sysfsLinux 把裝置表示成 /dev 底下的檔案，讀寫用 read／write，特殊命令用 ioctl；sysfs（/sys）用一個屬性一個檔案的方式公開設定
copy_from_user／copy_to_userkernel 跟 user 交換資料的專用函式，會檢查位址合法。不能直接拿 user 給的指標來用
驅動分層子系統核心（例如 i2c-core）在中間；下面是控制器驅動（adapter，對應 SoC 的 I²C 硬體）；上面是裝置驅動（client，對應掛在匯流排上的某顆 IC）
Platform driver給 SoC 內建、不能自動列舉的週邊用的驅動類型，靠裝置樹描述來配對
Device tree（裝置樹）描述硬體的資料檔：原始檔 .dts，用 dtc 編譯成 .dtb，開機時由 bootloader 交給 kernel。常見屬性 compatible、reg、interrupts、status、pinctrl
Overlay（.dtbo）疊加在基本裝置樹上的補丁，例如在 &i2c1 底下加一顆裝置、把 status 從 disabled 改 okay
Probe／deferred probecompatible 配對成功後 kernel 呼叫驅動的 probe() 初始化裝置；它需要的 GPIO、regulator、clock 還沒好時回傳 -EPROBE_DEFER，晚點再試
Interrupt context在中斷處理中執行的狀態，不屬於任何 process，不能睡覺（不能等 mutex、不能呼叫可能 sleep 的函式）
KMDF／UMDF、WinUSBWindows 的驅動框架：KMDF 在 kernel、UMDF 在 user mode。WinUSB 是微軟內建的通用 USB 驅動，應用程式可以直接透過它傳 USB 封包，不必自己寫 kernel 驅動

L2為什麼

  • 為什麼要分 kernel 和 user？保護與隔離。user 程式寫錯只會讓自己那個 process 當掉；kernel 驅動寫錯（例如亂指標）會拖垮整台機器：Linux 是 kernel oops／panic，Windows 是藍屏。所以能在 user space 做的就不要進 kernel。
  • 為什麼驅動要分控制器和裝置兩層？面板 IC 的驅動只想說「寫暫存器 0x51 = 0x80」，不想管這顆 SoC 的 I²C 控制器要怎麼設。分層後，一支 IC 驅動配任何 SoC 都能用，換 SoC 只要換控制器驅動。
  • 為什麼用裝置樹而不是寫在程式裡？ARM 板子成千上萬種，週邊位址、腳位、IRQ 都不同。寫成資料檔，同一份 kernel 二進位就能跑多塊板子；改板子只改 .dts、不重編驅動。
  • 中斷裡為什麼不能睡？中斷不是一個可被排程的 thread，睡下去沒人能叫醒；而且被打斷的程式可能正抓著你要等的鎖，等於自己等自己。中斷裡只能用 spinlock；要做會睡的事（等 I²C 傳完），改用 threaded IRQ 或 workqueue 交給一般 thread。
  • user space 驅動什麼時候夠用？低速、不要求即時的裝置：Linux 有 i2c-dev、spidev 可以直接從 user 傳 I²C／SPI；Windows 上 C# 工具透過 WinUSB、HID 或虛擬 COM port 跟 IC 評估板溝通，完全不用寫 kernel 驅動，當掉也不會藍屏。需要處理中斷、高頻寬、或給其他子系統（顯示、輸入）用時才寫 kernel 驅動。
  • 大量資料怎麼避免來回複製？read／write 每次都要在 kernel 與 user 之間複製。影像 buffer 這類大資料用 mmap 把 kernel 的記憶體直接映射給 user，省掉複製。

L3出問題怎麼辦

現象最可能原因對策
驅動編進 kernel 了，probe() 卻從來沒被呼叫裝置樹的 compatible 字串跟驅動的 of_match_table 不一致（一個字母都不行）、節點 status 是 "disabled"、驅動模組沒載入比對兩邊 compatible 字串；status 改 "okay"；確認模組已載入、kernel 設定有開

容易混淆

這兩個差在哪
ISP vs IAP vs OTA晶片內建 ROM bootloader 燒錄 vs 自己的程式在執行中寫 Flash vs 透過網路做 IAP（ISP 段）
CRC vs 簽章防意外損毀、誰都算得出來 vs 防竄改、要私鑰才產得出來（K01）
Rollback vs anti-rollback新版失敗時退回舊版（好事） vs 禁止刷回舊版（安全）。兩者會互相牽制：已確認的版本才往上加計數（K01）
Vector table vs VTOR中斷進入點的那張表 vs 告訴 CPU 那張表在哪的暫存器（K01）
volatile vs atomic每次都真的存取 vs 存取不可被打斷。volatile 不保證 atomic（K02）
W1C vs RC vs RW寫 1 才清 vs 讀了就清 vs 一般讀寫（K02）
Cortex-M 優先權數字 vs 急迫程度數字越小越急；0 是最高優先權（K03）
Push-pull vs open-drain上下都推、快 vs 只會拉低、高電位靠上拉、可共線與轉電壓（K04）
IWDG vs WWDG獨立時脈、只管太晚 vs 主時脈、太早太晚都 reset、有早期警告中斷（K04）
Spinlock vs mutex拿不到就原地等、中斷裡可用 vs 拿不到就睡、中斷裡不能用（K05）
.dts vs .dtb vs .dtbo裝置樹原始檔 vs 編譯後給 kernel 的二進位 vs 疊加用的 overlay（K05）
Kernel 驅動 vs user space 驅動能處理中斷、效能高、寫錯會拖垮系統 vs 開發簡單、當掉只影響自己（K05）
