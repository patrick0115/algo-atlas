觀念圖鑑 ／ O AI 輔助開發

AI 輔助開發：模型負責寫，人負責定義「什麼叫做完」

coding agent 是一個反覆「讀 → 想 → 呼叫工具 → 改 → 驗證」的迴圈。它只看得到 context 裡的東西、只做得到權限允許的事、只會在「看起來完成」時停下來。所以人能控制的三件事決定了品質：給它什麼資訊（context）、允許它做什麼（權限）、用什麼證明它做對了（驗收條件、測試、review）。

對應 taxonomy O01～O06。難度標籤：L1是什麼　L2為什麼　L3出問題怎麼辦。

主圖：一步一步看 coding agent 的工作迴圈

    O01需求描述與任務拆分

    一句話：agent 會在「看起來做完」時停下來，所以需求裡最重要的不是「做什麼」，而是「怎樣算做完」——寫成可以跑、可以判斷對錯的驗收條件，再把大任務拆成每一步都能單獨驗證的小步。

    L1是什麼

    名詞意思
    自然語言規格（spec）用人話寫的需求說明。好的 spec 至少有：目標、背景（相關檔案與介面）、限制、驗收條件、範圍外（out of scope）
    驗收條件（acceptance criteria）判斷「完成」的具體條件，必須能被檢查：輸入→預期輸出、測試名稱、build 通過、截圖比對、效能門檻
    Given-When-ThenBDD（行為驅動開發）的情境寫法：Given 前提狀態、When 動作、Then 預期結果。一條就是一個可寫成測試的案例
    EARSRolls-Royce 在 2009 年發表的需求句型：一般（The system shall…）、事件（When…）、狀態（While…）、異常（If…then…）、選配（Where…）。強迫把觸發條件寫出來
    任務拆分把大需求切成多個小步，每步產生一個能單獨 review、單獨測試、單獨 commit 的 diff
    計畫模式（plan first）先讓 agent 只讀不寫，產出「要改哪些檔、順序、風險」的計畫，人審過再動手
    Definition of Done團隊層級的完成定義（例：有測試、有文件、review 過），每個任務都要滿足
    反問／訪談（interview）需求還沒想清楚時，先讓 AI 反過來問你邊角情況與取捨，問完寫成 spec，再開新 session 實作

    L2為什麼

    • 為什麼驗收條件比實作步驟更重要？agent 沒有可以跑的檢查時，「看起來完成」就是它唯一的停止訊號，人就變成每個錯誤的偵測器。給它測試、build、比對腳本這類會回傳通過／失敗的東西，它可以自己「改 → 跑 → 讀結果 → 再改」直到通過，迴圈自己閉合。
    • 為什麼要寫「不做什麼」？模型傾向「多做一點看起來比較完整」：順手重構、加防呆、改格式。範圍外清單直接排除這些，也讓 review 時一眼看出超出範圍的修改。
    • 為什麼要拆小步？每一步的 diff 小，人才看得完；某一步錯了只要退那一步；方向錯了在第一步就發現，而不是整個功能寫完才發現解錯問題。
    • 什麼時候不用先計畫？如果能用一句話描述 diff（改錯字、加一行 log、改變數名），直接做就好；計畫適合「不確定做法、會改多個檔、不熟那段 code」的情況，否則只是多一層成本。
    • 為什麼 spec 寫完要開新 session 實作？訪談過程的來回討論會佔 context，而且混著被否決的想法；新 session 只讀定稿的 spec，焦點乾淨。
    • 好 spec 的實務格式？點名相關檔案與介面、說明範圍外、最後一條是端到端驗證（例：跑完整回歸集，輸出與基準相同）。對工具開發來說，「既有樣本的輸出不能變」通常是最有用的一條。

    L3出問題怎麼辦

    現象最可能原因對策
    AI 說「完成了」，實際一跑就錯沒有可執行的驗收條件，它只能用「看起來對」判斷需求裡寫明要跑的測試或比對指令，並要求它貼出執行結果當證據
    只要求修一個 bug，diff 卻改了十幾個檔沒寫範圍與「不做什麼」，AI 自行擴大修改指定檔案範圍與範圍外清單；超出的部分退回重做，不要整包接受
    寫了一大段功能才發現解錯問題跳過計畫直接實作；需求的關鍵假設沒確認多檔修改先要計畫、人審過再動；計畫裡列出它的假設讓你逐條確認
    同一件事來回糾正好幾次還是錯context 已經塞滿失敗的嘗試，越改越亂糾正兩次不成就清掉 context，把學到的限制寫進新的、更具體的需求重來
    測試都過了，但使用者說不是他要的驗收條件只測了實作細節，沒對應到使用者情境用 Given-When-Then 從使用者動作寫情境；把真實的使用者回報檔當測試樣本

    O02上下文管理與程式庫理解

    一句話：context window 是模型這一輪的全部視野，系統提示、規則檔、對話、讀過的檔案、工具輸出全部擠在裡面；塞得越滿，注意力越分散，所以要精準給、隨時清、需要時才讀。

    L1是什麼

    名詞意思
    Context window模型單次能讀取與處理的 token 上限。模型沒有長期記憶，每次回應都把整個 context 重讀一遍；不在 context 裡的，它看不到
    Token模型處理文字的單位，約等於一個英文單字的一部分或一兩個中文字。程式碼、log 都很吃 token
    Context rot輸入越長、表現越差的現象。Chroma 2025 年測 18 個模型，連簡單任務都隨長度下降，干擾資訊越多掉越快
    Lost in the middle資訊在長 context 中段時最容易被忽略，開頭與結尾最好（U 形）
    Compaction（壓縮）context 快滿時把前面的對話摘要成短文，再接著做。細節會遺失，早期的口頭指示可能被摘掉
    專案規則檔放在 repo 裡、每個 session 開始就自動載入的 Markdown 指示檔（如 CLAUDE.md、AGENTS.md、copilot-instructions.md）。放 build 指令、命名慣例、專案特有的陷阱
    分層規則使用者層（所有專案）→ 專案層（進版控、團隊共用）→ 本機層（不進版控）；有些工具還能讓規則只在碰到特定路徑時才載入
    Just-in-time 讀取不預先把檔案全部讀進來，只記路徑，需要時再用 grep／glob／讀檔工具抓
    清除 context換到不相關的任務時把對話整個清掉，從乾淨的視野開始

    L2為什麼

    • context 很大，為什麼還要省？上限是「放得下」，不是「看得清」。transformer 每個 token 都要和其他 token 建立關係，長度增加時注意力被攤薄，加上 lost in the middle，塞一堆無關檔案反而讓關鍵那幾行被淹沒。精準給 3 個相關檔通常勝過丟整個資料夾。
    • 規則檔為什麼要短？它每個 session 都佔 context；寫太長，重要的規則反而被雜訊淹沒而被忽略。官方文件建議單檔 200 行內，每行自問「拿掉它 AI 會犯錯嗎？」不會就刪。能從 code 讀出來的（目錄結構、套件清單）不必寫。
    • 規則檔寫了，為什麼 AI 還是偶爾不照做？規則檔是「放進 context 的建議」，不是強制設定；寫得模糊或兩條互相矛盾時，模型可能挑一條。一定要每次發生的事（例：每次編輯後跑格式檢查、禁止寫某目錄）要改用 hook 或權限設定這類由工具強制執行的機制。
    • 規則要寫成什麼樣才有效？具體到可以檢查：「縮排用 4 個空白」勝過「格式要整齊」；「API handler 放在 src/api/」勝過「檔案要有條理」。只對某類檔案有用的規則，改成只在碰到那類檔案時才載入。
    • agent 怎麼理解一個陌生的 code base？和人一樣：先讀規則檔與 README，再用搜尋找入口點和關鍵字，順著呼叫關係讀，最後才改。常見的混合策略是「規則檔一開始就載入、其他檔案用搜尋工具需要時才讀」。大範圍的探索交給 subagent，只帶回摘要，主對話的 context 不被一堆檔案內容佔掉。
    • 壓縮後為什麼會「忘記」？摘要只保留它判斷重要的東西。只在對話中口頭講過的要求，壓縮後可能消失；寫進規則檔的會被重新載入。所以重複講第二次的要求，就該寫進規則檔。

    L3出問題怎麼辦

    現象最可能原因對策
    對話很長之後，AI 開始違反一開始講好的規則context 壓縮把早期口頭指示摘掉了，或注意力被大量工具輸出稀釋重要規則寫進規則檔（壓縮後會重新載入）；換任務就清 context；冗長的探索交給 subagent
    AI 自己重寫了一份 repo 裡早就有的 helper它沒讀到既有實作，context 裡沒有那段需求裡點名「參考 XxxHelper.cs 的寫法」；規則檔寫「新增工具函式前先搜尋既有實作」
    規則檔明明寫了，AI 還是照自己的習慣做規則檔太長或互相矛盾，那一條被淹沒；或寫得太模糊刪減到只剩「拿掉會出錯」的規則、改成可檢查的具體句；必須強制的改用 hook／權限設定
    叫它「先看懂整個專案」之後，回答越來越不準一次讀進太多檔案，context 被塞滿、關鍵資訊在中段被忽略縮小調查範圍、指定入口檔；或讓 subagent 在獨立 context 探索，只回報摘要
    AI 引用的函式簽章跟實際檔案不一樣它讀到的是舊版內容（檔案在對話中被改過），或根本沒讀、憑印象寫要求修改前重新讀檔；回答時引用檔名與行號，方便你核對
    規則檔裡的某條規則 AI 完全沒照做，像是根本沒看到規則檔沒被載入：放錯位置或層級（例：放在子資料夾，只有讀到那個資料夾的檔案時才載入）；或 context 裡大量既有程式碼的寫法和規則相反，模型跟著範例走先用工具的記憶／規則檢視功能確認這份檔案有沒有被載入；放到會在開場載入的位置；需求裡點名要依規則改，必要時用 hook 或檢查腳本強制
    多個專案的規則互相打架使用者層與專案層規則矛盾，模型隨機挑一條專案特有的寫在專案層、通用的寫在使用者層，並定期檢查有無衝突

    O03Agent、Tool Calling、MCP

    一句話：模型本身不執行任何東西，它只輸出「我要呼叫哪個工具、參數是什麼」；真正執行的是外面的程式（client），而 client 先過權限這一關。MCP 是把「工具怎麼接上來」標準化的協定。

    L1是什麼

    名詞意思
    Agent會自己決定下一步、反覆呼叫工具直到任務完成的 LLM 系統；相對於「問一句答一句」的聊天
    Tool calling／function calling開發者用 JSON Schema 描述工具（名稱、說明、參數），模型回傳結構化的呼叫要求，client 執行後把結果送回
    MCP（Model Context Protocol）Anthropic 在 2024-11-25 發表的開放協定，讓 AI 應用（client）用同一種方式接各種外部系統（server）。2025-12-09 捐給 Linux Foundation 旗下的 Agentic AI Foundation
    MCP 的三種能力server 可提供 tools（可執行的動作）、resources（可讀的資料）、prompts（範本）
    MCP 傳輸方式訊息用 JSON-RPC。stdio：client 把 server 當子行程啟動，走標準輸入輸出，適合本機；Streamable HTTP：server 是獨立服務，取代 2024-11-05 版的 HTTP+SSE
    權限規則allow（直接放行）、ask（每次問）、deny（禁止）。常見的判定順序是 deny 先、再 ask、最後 allow，allow 不能在 deny 上開例外
    Sandbox作業系統層級限制 agent 能碰的檔案與網路，即使指令寫法繞過了規則也出不去
    Subagent由主 agent 派出、在獨立 context 工作的子 agent，可限制工具，做完只回傳摘要
    Hook在固定時間點（例：工具執行前、編輯後）由工具強制執行的腳本，可用來擋危險指令或自動跑檢查

    L2為什麼

    • 為什麼需要 MCP？沒有標準時，每個 AI 應用接每個系統都要各寫一次（M×N）。MCP 讓系統只要包成一個 server，所有支援 MCP 的 client 都能用（M＋N）。對公司內部工具特別有用：把內部資料庫或量測系統包成 server，就能被 agent 查詢。
    • 為什麼權限要在 client 端擋，不能寫在提示裡請模型不要做？模型分不清「你的指示」和「工具結果裡夾帶的指示」。讀到的網頁、文件、issue 內容都可能藏著惡意文字（prompt injection）。規則檔只是建議，權限規則和 sandbox 才是不管模型怎麼想都會生效的硬邊界。
    • 什麼是 lethal trifecta？同一個 agent 同時有「讀得到機密」「會讀不可信內容」「能對外傳送」三種能力時，攻擊者只要讓它讀到一段惡意文字就能偷資料。拆掉其中一項（例：處理外部文件的 agent 不給網路）就能大幅降低風險。
    • MCP server 本身為什麼也是風險？工具描述是給模型看的，使用者通常看不到全文。惡意 server 可以在描述裡藏指示（tool poisoning）、通過審核後再偷改描述（rug pull）、或影響其他可信工具的行為（shadowing）。只裝信任來源、固定版本、看過完整描述再用。
    • 什麼時候該開 subagent？工作會產生大量輸出（跑測試、掃整個 repo、查文件）、可以獨立完成、只需要回傳結論時。它的價值是讓主對話的 context 保持乾淨。不適合：要頻繁來回確認的、多個階段共用大量脈絡的、只是一個小改動的（啟動時要重新蒐集脈絡，反而慢）。
    • 多開幾個 agent 平行做，為什麼不一定划算？Anthropic 自己的研究系統中，agent 約用聊天的 4 倍 token、多 agent 系統約 15 倍。適合廣度優先、能切成獨立方向的研究；多數寫 code 的任務彼此相依，能真正平行的部分比研究少，平行還可能互相改到同一個檔。

    L3出問題怎麼辦

    現象最可能原因對策
    AI 讀了一份外部文件後，突然想把設定檔內容送到某個網址文件裡藏了 prompt injection，模型把它當成指示對外連線預設 deny 或只允許白名單網域；處理不可信內容的工作不給機密讀取權；啟用 sandbox
    設了禁止 rm 的規則，檔案還是被刪了規則比對的是指令文字，換個寫法（腳本、其他程式）就繞過去指令規則不是安全邊界；重要的限制用 sandbox 檔案系統隔離，並保持 git 可回復
    接了一個 MCP server 後，agent 行為怪怪的、會做沒要求的事工具描述藏有指示（tool poisoning）或版本更新後描述被改（rug pull）移除該 server、只用信任來源、固定版本、檢視完整工具描述
    每個動作都跳權限確認，最後都直接按同意權限設定太保守，人開始 rubber-stamp，確認失去意義把確定安全的唯讀與測試指令加 allow，危險的加 deny，只讓真正需要判斷的進 ask
    開了三個 subagent 同時改同一個 repo，出現衝突或 git lock 錯誤平行寫入同一個工作目錄寫入工作不要平行在同一個目錄；需要平行就各開獨立的 worktree，或只讓 subagent 做唯讀調查
    MCP 工具接太多，一開始 context 就被吃掉一大塊每個工具的 schema 都佔 context只啟用這個專案需要的 server；用支援「需要時才載入工具定義」的設定

    O04RAG 與程式碼搜尋

    一句話：context 放不下全部資料時，就先檢索出相關的幾段再交給模型（RAG）。找程式碼有兩種尺：關鍵字找「長得一樣的字」，embedding 找「意思相近的段落」，各有盲點，實務上常合併使用。

    L1是什麼

    名詞意思
    RAG（Retrieval-Augmented Generation）Lewis 等人 2020 年提出：先從外部資料檢索相關段落，再和問題一起交給模型生成答案。模型參數裡的知識叫參數記憶，外部索引叫非參數記憶
    Chunking（切塊）把文件或程式切成小段再建索引。程式碼常依函式、類別這種語法邊界切，避免一個函式被切成兩半
    Embedding把一段文字轉成一組數字向量，意思相近的文字向量距離也近（常用 cosine similarity 比較）
    向量索引（vector index）存放所有 chunk 向量的資料庫，用近似最近鄰（ANN）快速找出最像的前 k 個
    BM25經典的關鍵字排序公式：詞出現越多、越稀有、文件越短，分數越高。常用參數 k₁ 1.2～2.0、b 0.75
    混合檢索（hybrid）關鍵字與語意兩種結果合併。RRF（Reciprocal Rank Fusion）只看名次不看分數，常用常數 k＝60，不需要調參
    Reranker對初步撈出的候選再用較準的模型重新排序，只保留最相關的幾段
    Agentic search不預建索引，讓 agent 自己反覆下 grep／glob、讀檔、再決定下一個關鍵字，像人一樣邊找邊縮小範圍
    Top-k檢索取回的段落數。太少漏掉、太多又把 context 塞滿

    L2為什麼

    • 為什麼找程式碼時關鍵字搜尋特別強？程式碼充滿精確識別字：函式名、暫存器名、錯誤訊息、設定 key。這些「一字不差」的查詢，grep 一定找得到而且完整；embedding 把意思相近的都拉進來，反而可能漏掉或混進近似名稱。
    • 那 embedding 什麼時候贏？你不知道確切名稱、只知道概念時（「哪裡處理逾時重送？」「跟 gamma 校正有關的程式在哪？」），或用中文問、程式用英文寫時。
    • 為什麼不乾脆把整個 repo 塞進 context？大部分 repo 放不下；放得下也會遇到 context rot 與成本問題。反過來，資料量真的小（Anthropic 的建議門檻是 20 萬 token、約 500 頁內）就直接整份放進 prompt，比建 RAG 簡單。
    • agentic search 與預建索引各有什麼取捨？agentic search 每次都讀最新的檔案、不必維護索引、不必把程式碼上傳到索引服務，代價是多花幾輪工具呼叫；預建向量索引查詢快、適合超大 repo 或概念查詢，但會過期（程式改了索引沒更新）、切塊可能切壞語意，而且索引要存在某處，需要評估機密性。
    • 為什麼切塊方式影響很大？檢索的最小單位就是 chunk。函式被切成兩半，撈回來的只有一半；chunk 缺少「屬於哪個類別、哪個檔」的上下文時也容易誤判。Anthropic 實驗在每個 chunk 前補一句脈絡說明，檢索失敗率降 35%，再加 BM25 降 49%，再加 rerank 降 67%。

    L3出問題怎麼辦

    現象最可能原因對策
    問某個暫存器名或錯誤碼，AI 找到的都是不相干的段落只用語意搜尋，精確識別字不是它的強項精確字串改用 grep／關鍵字；系統面做混合檢索
    AI 引用的程式碼和目前檔案不一樣向量索引過期，撈到的是舊版 chunk改檔後重建或增量更新索引；最終修改前一律重新讀實際檔案
    內部規格書 RAG 問答常引用舊版規格的內容新舊版文件同時留在索引裡，chunk 沒有版本、日期等 metadata 可過濾；或新版上架後索引沒更新舊版移出索引或標記作廢；每個 chunk 帶文件名、版本、日期 metadata，查詢時只取最新有效版；回答附出處與版本讓人核對
    撈回來的段落只有半個函式，AI 推論出錯依固定字數切塊，切斷了語法結構依函式／類別邊界切；chunk 附檔名與所屬類別等脈絡
    撈很多段進來，答案反而變差top-k 太大，雜訊稀釋了關鍵資訊降低 k、加 reranker 只留最相關的幾段
    用中文描述功能，搜不到英文寫的程式關鍵字搜尋不跨語言用語意搜尋，或請 AI 先把概念翻成可能的英文識別字再 grep
    公司擔心原始碼被上傳到外部索引服務預建雲端索引需要把程式碼片段或向量送出去評估工具的索引存放位置與保留政策；敏感 repo 改用本機搜尋（agentic search）或停用索引

    O05Diff Review 與回復機制

    一句話：AI 寫得快，所以瓶頸移到人看不看得完、驗不驗得了、退不退得回去：diff 要小、review 要對照驗收條件、測試要當閘門、每個可運作的狀態都要 commit。

    L1是什麼

    名詞意思
    Diff修改前後的差異，逐行標出新增（+）與刪除（−）。review AI 修改的主要依據
    Code review由人（或另一個獨立的 AI）檢查 diff 是否正確、符合需求、沒有超出範圍
    測試閘門（test gate）build、單元測試、回歸測試沒通過就不准合併；可在 CI 或本機 hook 強制
    回歸測試用一組既有樣本確認「原本對的還是對的」。改 parser、演算法時最重要
    git revert新增一個 commit 抵銷指定 commit 的效果，不改寫歷史
    git reset把分支指標移回較早的 commit，之後的 commit 從歷史中拿掉；--hard 連工作目錄的修改也丟掉
    git stash把工作目錄裡還沒 commit 的修改暫時收起來，讓工作目錄回到乾淨狀態；之後用 git stash pop 拿回來。適合「先讓 AI 試別的做法，原本的改到一半先放旁邊」
    Checkpoint／rewindagent 工具在每輪對話前自動存的檔案快照，可退回；只涵蓋自己編輯工具改的檔，是 session 層級的救急，不是版本控制
    Branch／worktreebranch 讓實驗和主線分開；worktree 讓同一個 repo 同時有多個工作目錄，平行的 session 各改各的不衝突
    Writer／Reviewer一個 session 寫，另一個乾淨 context 的 session（或 subagent）只看 diff 與驗收條件來 review

    L2為什麼

    • 為什麼 diff 要小？人一次能認真看的行數有限，800 行跨 20 檔的 diff 最後一定變成「大概看一下」。小 diff 也讓錯誤容易定位、容易單獨退回。
    • review AI 的 code 要特別看什麼？對照驗收條件逐條確認；看有沒有超出範圍的修改（格式、import、無關重構）；新增的套件與 API 是否真的存在；有沒有刪掉檢查或錯誤處理；有沒有寫死路徑、帳密；測試檔有沒有被改。
    • 為什麼要讓另一個 context 來 review？寫 code 的那個 session 帶著自己的推理，容易替自己的修改找理由；乾淨 context 只看 diff 與標準，比較能發現盲點。但 reviewer 被要求「找問題」就一定會找出一些，要叫它只報影響正確性或需求的問題，否則會被帶去過度設計。
    • 測試為什麼要防 AI 自己改？測試失敗時，最省事的「修法」是改 assert、跳過測試或刪掉案例。所以 diff 裡有測試檔變動時要特別看：是修正測試本身的錯，還是把標準降低了。
    • 為什麼要小步 commit？每個可運作的狀態都是一個安全點。壞了只要退一步；不 commit 的話，一整天的修改只能整包丟掉或手動挑。agent 的回復點不追蹤 shell 改的檔，git 才是最後防線。
    • revert 和 reset 怎麼選？已經推到共用 remote 的用 revert（不改寫別人已經拿到的歷史）；還在本機、沒推出去的才用 reset。

    L3出問題怎麼辦

    現象最可能原因對策
    合併後才發現 AI 改了好幾個不相關的檔沒看 diff 就全部接受（rubber-stamp），或 diff 太大看不完要求每次只改指定範圍；review 先看「改了哪些檔」清單，超出範圍的直接退
    測試忽然全部變綠，但功能其實沒修好AI 改了測試的預期值、加了 skip 或刪掉 assert測試檔變動要單獨審；規則檔寫「不得修改既有測試的預期值，除非我同意」
    bug 已經推上共用分支，要退回錯誤的 commit 已被別人拉走用 git revert 產生反向 commit，不要 reset＋強制推送
    用 agent 的回復功能退了，檔案還是被改過那些檔是用 shell 指令改的（或是 subagent、其他程序改的），回復點沒追蹤開工前確認工作目錄乾淨、先 commit；最後用 git 比對與還原
    想試兩種做法，結果互相覆蓋在同一個工作目錄來回試每種做法開一個 branch 或 worktree，比較完留下一個
    改了 parser 之後，舊樣本的結果默默變了只測了新案例，沒跑回歸集建立固定回歸樣本與基準輸出，每次修改都比對，差異逐一確認是改善還是退步

    O06AI 開發風險

    一句話：AI 產出的 code「看起來對」的比例遠高於「真的對」；五大風險是幻覺、過度修改、相依套件、機密外洩、可維護性，每一項的對策都是同一句：人要看得懂、驗得了，才合併。

    L1是什麼

    名詞意思
    幻覺（hallucination）模型自信地產生不存在或錯誤的東西：不存在的 API、參數、套件、設定值、規格數字
    套件幻覺／slopsquattingAI 建議安裝不存在的套件名；攻擊者搶先註冊這些名字放惡意程式。2024 年研究分析 16 個模型、57.6 萬份程式樣本，商用模型至少 5.2%、開源模型 21.7% 的建議套件不存在，共出現 205,474 個不同的假套件名
    過度修改（over-editing）超出需求的修改：順手重構、改格式、改 import 排序、加沒要求的功能或防呆
    供應鏈風險依賴的套件、模型、MCP server 本身被植入惡意程式或有漏洞（OWASP LLM Top 10 2025 的 LLM03）
    敏感資料外洩把原始碼、客戶資料、帳密貼給外部 AI 服務，或 agent 讀到 .env 後外送（OWASP LLM02）。2023 年 4 月三星員工把內部原始碼與會議內容貼進 ChatGPT，5 月公司暫時禁用生成式 AI
    Excessive agency給 agent 的權限、功能、自主程度超過任務需要（OWASP LLM06）
    可維護性未來的人（包括三個月後的自己）能不能看懂、修改、除錯這段 code

    L2為什麼

    • 為什麼會幻覺？模型是依機率接續最像的文字，不是查資料庫。常見的命名模式（例：xxx.Utils、ToAsync()）會被「合理地」生成出來，即使實際不存在；訓練資料的截止日也讓它不知道新版 API 的變動。
    • 為什麼套件幻覺是安全問題，不只是編譯錯？同一個假名字會被不同人重複問到時反覆出現，攻擊者可以預先註冊它。照著 AI 的建議直接 install，就把惡意程式裝進來了。對策：安裝前查官方套件庫的發布者、下載量、建立日期；公司環境走內部鏡像與核准清單。
    • 為什麼 AI 傾向過度修改？它想讓結果「看起來更完整」，又看不到團隊的隱性慣例（例：WinForms 的 Designer 檔不能亂排、某些格式是工具要讀的）。過度修改的成本在 review：真正的變更被淹沒在格式差異裡。
    • 為什麼 AI 產的 code 安全性要特別審？Veracode 2025 年的報告中，45% 的程式樣本引入 OWASP Top 10 漏洞，Java 72%、C# 45%；而且模型越新越大，安全表現並沒有跟著變好。功能正確不等於安全。
    • 為什麼「感覺變快」不一定是真的變快？METR 2025 年的實驗中，16 位資深開源開發者在自己熟悉的大型專案上用 AI 工具，完成任務反而慢了 19%，但事後仍覺得快了 20%。省下的打字時間，可能被等待、修正、review 吃回去；越熟的 code base 越明顯。
    • 可維護性為什麼是長期風險？看不懂就合併的 code，出問題時沒人能修，只能再叫 AI 改，越改越難懂。規則：自己解釋不出這段在做什麼，就不要合併。

    L3出問題怎麼辦

    現象最可能原因對策
    AI 寫的程式呼叫一個編譯不過的方法API 幻覺，或該方法在你用的版本不存在要它先查實際的套件版本與文件；以編譯與測試結果為準，不信它的說明
    AI 建議裝一個從沒聽過的套件可能是幻覺套件名，甚至已被搶註成惡意套件先到官方套件庫查發布者、下載量、建立日期；能用既有套件或標準函式庫就不新增；新增依賴要人決定
    修一個小 bug，diff 裡一半是格式與 import 變動過度修改；AI 套用了自己的格式偏好規則檔寫「只動需求範圍、不改無關格式與 import」；用格式工具統一後再比對；超出部分退回
    API Key 被寫死在原始碼裡，差點 commitAI 為了「能跑」把密鑰直接填進去密鑰放加密的本機儲存或環境設定，不進版控；commit 前跑 secret scanning；已推出去的金鑰立即作廢重發
    同事把含 API Key 或密碼的 log 整段貼給雲端 AI 除錯貼之前沒遮罩敏感字串；內容一送出就離開公司控制，刪掉對話紀錄不能保證服務端沒留存視同已外洩：立即作廢並換發該金鑰；確認該服務的資料保留與訓練使用政策；之後先把密鑰、客戶資料遮罩再貼
    同事把客戶規格書整份貼進公開 AI 服務沒有資料分級與核准的 AI 使用管道公司提供經核准的 AI 入口（內部 gateway）；明訂哪些資料不能送出；agent 設 deny 讀取機密目錄
    半年後沒人看得懂某個模組，只能整段叫 AI 重寫當初看不懂就合併；缺乏設計說明合併前要求自己能解釋每段；重要決策寫進文件或 commit 訊息；拆成小而清楚的單元

    容易混淆

    這兩個差在哪
    Context window vs 訓練資料這一輪看得到什麼（暫時、有上限）vs 模型學過什麼（固化在參數裡、有截止日）（O02）
    規則檔 vs hook／權限設定放進 context 的建議，模型可能不照做 vs 工具強制執行，不管模型怎麼想都生效（O02、O03）
    Tool calling vs MCP模型呼叫工具的機制 vs 工具怎麼接到 client 的標準協定；MCP 的工具最後也是透過 tool calling 被呼叫（O03）
    Subagent vs 平行 session主 agent 派出、獨立 context、只回摘要 vs 人自己開的多個獨立對話，要自己協調；兩者寫同一個目錄都會衝突（O03）
    RAG vs fine-tuning執行時把外部資料檢索進 context，資料改了馬上生效 vs 用資料重新訓練模型參數，改資料要重訓（O04）
    關鍵字搜尋 vs embedding 搜尋找字面一樣的，識別字精準 vs 找意思相近的，概念查詢強但可能混進近似名（O04）
    Agentic search vs 向量索引即時 grep、永遠是最新檔案、多花幾輪呼叫 vs 預建索引查詢快、會過期、要存放程式碼向量（O04）
    git revert vs git reset新增反向 commit、不改寫歷史 vs 移動分支指標、改寫歷史（O05）
    Checkpoint vs git commitagent 的 session 層級快照，只追蹤自己編輯工具改的檔 vs 永久、完整的版本歷史（O05）
    驗收條件 vs 實作步驟怎樣算完成（可檢查）vs 怎麼做；前者決定 agent 何時停，後者可以交給 agent 想（O01）
    幻覺 vs 知識過時產生根本不存在的東西 vs 東西存在但已經改版；對策都是查實際版本的文件與編譯結果（O06）
    Prompt injection vs 越獄（jailbreak）第三方把指示藏在 agent 會讀的內容裡 vs 使用者自己誘導模型違反限制（O03、O06）
