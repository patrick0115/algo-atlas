作業系統與系統程式：程式底下那一層在忙什麼

你寫的每一行程式，底下都有作業系統在幫你分時間（排程）、分空間（虛擬記憶體）、管共用（鎖與同步），再往下是 CPU 用 cache 與 pipeline 猜你下一步要什麼。大部分「偶發、時好時壞、跑久才出事」的 bug，都是這幾層的假設被打破了。

I01Process 與 Thread

一句話：Process 是「一份獨立的記憶體空間＋資源」，thread 是「在這份空間裡跑的一條執行流程」；作業系統的排程器不斷在它們之間切換，讓大家看起來同時在跑。

L1是什麼

名詞意思
Process（行程）執行中的程式：自己的虛擬位址空間、開啟的檔案、權限。Process 之間互相看不到記憶體
Thread（執行緒）process 裡的一條執行流程，有自己的暫存器與 stack，共用同一個 process 的 heap、全域變數、檔案
PCB（Process Control Block）核心替每個 process 存的一份紀錄：PID、父行程、狀態、頁表位置（它的虛擬記憶體地圖）、開了哪些檔案／handle、權限、底下有哪些 thread。管「這個程式擁有什麼」
TCB（Thread Control Block）核心替每個 thread 存的一份紀錄：狀態（執行中／就緒／等待）、暫存器快照（含 PC＝下一行要跑哪、SP＝自己那塊 stack 頂端在哪）、優先權、屬於哪個 PCB。管「這條執行流程跑到哪」
排程（scheduling）決定下一個誰跑。搶占式（preemptive）：時間片到了或高優先權的來了就強制換人，現代桌面與伺服器 OS 都是；協作式：要等程式自己讓出。Linux 一般行程排程器在 6.6 版從 CFS 換成 EEVDF；Windows 是依優先權的搶占式排程
Context switch把目前 thread 的暫存器存回它的 TCB、從下一個 thread 的 TCB 載回來。換到別的 process 還要依 PCB 切換頁表
fork／execLinux 開新程式的兩步：fork 複製出一個子行程，exec 把它換成新程式。Windows 用 CreateProcess 一步完成（C# 的 Process.Start）
IPC行程間通訊：pipe（管線）、shared memory（共享記憶體）、message queue、socket、signal；Windows 另有 named pipe、memory-mapped file
殭屍行程（zombie）已結束，但父行程還沒用 wait() 讀走結束碼，ps 顯示狀態 Z、<defunct>。不吃 CPU、記憶體，只佔一個 PID
孤兒行程（orphan）父行程先結束，子行程還在跑，改由 init（PID 1）或指定的 subreaper 收養，之後由它負責 wait()
Daemon／Service背景常駐、不接終端機的行程。Linux 多由 systemd 管理；Windows 叫 Service

PCB、TCB 與記憶體的關係

PCB（一個 process）
├─ PID、父行程、權限
├─ 頁表位置 ──────────→ 這個 process 的虛擬記憶體（I02）
├─ 開啟的檔案／handle
├─ TCB（thread 1）── 狀態、暫存器、PC、SP ──→ stack 1
├─ TCB（thread 2）── 狀態、暫存器、PC、SP ──→ stack 2
└─ 所有 thread 共用：heap、.data／.bss、.text

Context switch（thread 1 → thread 2）
  ① CPU 暫存器（含 PC、SP）存進 TCB 1
  ② 從 TCB 2 載回暫存器 → CPU 從 thread 2 停下的那一行繼續，用 stack 2
  ③ 若 thread 2 屬於別的 process：再依它的 PCB 換頁表（TLB 也跟著失效，所以比較貴）

L2為什麼

  • 為什麼 thread 比 process 輕？同一個 process 的 thread 共用位址空間，建立時不用複製記憶體對應，切換時也不必換頁表、TLB 不用清掉。代價是一個 thread 寫壞記憶體，整個 process 一起死；process 隔離好但通訊要走 IPC。
  • 為什麼要有 PCB／TCB？CPU 一次只跑一條 thread，被換下來的 thread 必須「存檔」，下次才能從同一行、同一份 stack 接著跑；process 的記憶體地圖、開過的檔案也要有地方記，結束時核心才知道要收哪些資源。把「擁有的資源」（PCB）和「執行進度」（TCB）分開，同一個 process 才能有多條 thread 共用資源、各自進度。Linux 其實兩者都用 task_struct，process 與 thread 的差別只在建立時（clone）共用了多少；Windows 分成 EPROCESS 與 ETHREAD。
  • Context switch 的成本在哪？存取暫存器本身很快，貴的是間接成本：新 thread 的資料不在 cache、TLB 裡，要重新暖機。所以 thread 開幾千個、彼此一直搶鎖，CPU 時間會大量花在「換人」而不是做事。
  • 為什麼要有殭屍這個狀態？父行程可能想知道子行程的結束碼（成功或失敗），所以核心先保留那一格，等父行程來讀。父行程一直不讀，殭屍就一直在；kill -9 殭屍沒用，因為它已經死了。
  • IPC 怎麼選？同一台機器要大量資料又要快 → shared memory（最快，但要自己加同步）；簡單一進一出 → pipe（C# 重導外部程式的 stdout 就是 pipe）；可能跨機器 → socket；只是通知一聲 → signal／event。
  • 為什麼 UI 程式要分 thread？WinForms 只有一個 UI thread 在跑訊息迴圈（處理重繪、按鍵）。耗時工作放在 UI thread，訊息迴圈停住，視窗就「沒有回應」。工作要丟到背景（Task.Run、async/await），完成後再回 UI thread 更新畫面。

I02記憶體管理

一句話：每個程式拿到的是虛擬位址，CPU 的 MMU 透過頁表以 4 KB 一頁為單位翻成實體位址；翻譯結果快取在 TLB，頁不在記憶體時觸發 page fault 由作業系統補上。

虛擬空間裡怎麼切：同一片位址空間分成好幾區。程式碼、常數、全域變數在載入時就固定；heap 執行中要多少拿多少；stack 隨函式呼叫自動疊上、拿掉。

L1是什麼

名詞意思
虛擬記憶體每個 process 看到一整片自己的位址空間，實際放在哪塊實體記憶體（或磁碟）由 OS 決定
Page／Page frame虛擬空間切成固定大小的「頁」，實體記憶體切成同大小的「頁框」。x86 常用 4 KB，另有 2 MB／1 GB 大頁
頁表（page table）記錄「哪一頁對到哪個頁框、可讀寫執行嗎、在不在記憶體」。x86-64 四層：48-bit 位址＝4×9 bit 索引＋12 bit offset
TLBCPU 裡快取「頁 → 頁框」翻譯結果的小表，命中就不用 page walk
Page fault存取的頁目前沒對應到實體記憶體。minor：頁其實在記憶體（例如共用函式庫、第一次寫入的零頁），補個對應就好；major：要從磁碟讀進來，慢很多
Swap／分頁檔記憶體不夠時把少用的頁寫到磁碟。Windows 叫 pagefile
Stack（堆疊）每個 thread 一塊，放區域變數、函式返回位址，函式結束自動釋放。大小固定：Linux 主執行緒預設常見 8 MB（ulimit -s），Windows thread 預設 1 MB
Heap（堆積）動態配置（malloc／new），要自己釋放或由 GC 回收，大小可彈性成長
.text／.rodata.text 放機器指令（唯讀、可執行）；.rodata 放 const 常數與 "hello" 這種字串常值（唯讀，改它會 crash）
.data／.bss全域與 static 變數。有給初值的放 .data，沒給的放 .bss（載入時清成 0）。程式結束才消失
Stack frame每呼叫一次函式就在 stack 疊一格，放返回位址、參數、區域變數；函式 return 就拿掉。最後疊上的最先拿掉（LIFO）
Stack pointer（SP）CPU 暫存器，指著 stack 頂端。配置／釋放 stack 只是移動 SP，所以非常快
Call stack／stack trace目前疊著的那幾格 frame。VS 的「呼叫堆疊」視窗、例外訊息裡那串 at Xxx.Foo() line 42 都是它的快照，由上往下讀＝由內往外
Stack overflowframe 疊超過 stack 上限。常見於遞迴太深、函式裡開大陣列。.NET 碰到會直接結束整個程序，try/catch 抓不到
Managed heap／GC 世代.NET 的 heap 由 GC 管，分 Gen0／Gen1／Gen2：新物件進 Gen0，活過回收就升一代。大部分物件很快就死，所以 Gen0 收得最勤、最便宜
LOH（大型物件堆積）85,000 bytes 以上的物件（大陣列、大字串）另外放，跟 Gen2 一起才收，預設不壓實，容易破碎
Linker script韌體決定各區放在 Flash／RAM 哪個位址、多大的檔案（.ld／.icf／.sct）。PC 程式由 OS loader 決定，不必寫
Memory leak不再用的記憶體一直沒被釋放。有 GC 的語言也會：只要還有參考指著它，GC 就不收
對齊（alignment）資料放在自身大小整數倍的位址（4 byte 的 int 放在 4 的倍數）。編譯器會在 struct 欄位之間塞 padding 來對齊
VSZ／RSSVSZ：保留的虛擬空間總量；RSS：實際佔用的實體記憶體。看記憶體用量看 RSS（Windows 看「工作集」或「認可大小」）
OOM killerLinux 記憶體用盡時，核心挑一個行程殺掉保住系統，dmesg 會留下紀錄

L2為什麼

  • 為什麼要虛擬記憶體？三個好處：隔離（A 程式寫壞記憶體不會改到 B）、假裝很大（要用到才真的配頁，demand paging）、共用（同一個 DLL／.so 的程式碼頁，所有行程對到同一份實體頁）。
  • 為什麼頁表要分好幾層？48-bit 空間若用單層表，每個行程光頁表就要幾百 GB。分層後沒用到的區域整段不用建表，只在用到的地方展開。代價是 TLB 沒命中時要多讀好幾次記憶體，所以 TLB 命中率很重要。
  • Stack 為什麼快、為什麼會爆？配置只是把 stack 指標移一下，用完自動回收，而且剛用過的位置通常在 cache 裡。但大小固定：遞迴太深或在函式裡開超大區域陣列，就 stack overflow。大資料放 heap。
  • C# 有 GC 為什麼還會漏？GC 只收「沒有人參考」的物件。常見漏法：事件訂閱沒取消（發布者活多久，訂閱者就被抓多久）、static 集合只加不刪、快取沒上限。另外 Bitmap、Font、Graphics 背後是 GDI 這類非受控資源，GC 不急著收，要自己 Dispose（用 using）。
  • 為什麼要對齊？CPU 一次從 cache 抓一個對齊的區塊。沒對齊的資料可能跨兩個區塊、要讀兩次；x86 只是慢一點，部分 ARM Cortex-M0 等 MCU 直接 HardFault。解析韌體或暫存器 dump 的二進位格式時，不要把 byte 陣列的任意位置硬轉成 uint32 指標，改用 memcpy 或逐 byte 組。
  • 為什麼大頁能加速？同樣的 TLB 項數，一項涵蓋 2 MB 而不是 4 KB，大記憶體工作（資料庫、VM）TLB 沒命中次數大減。Linux 有手動的 HugeTLB 與自動的 Transparent HugePages。
  • 為什麼遞迴會吃 stack、迴圈不會？每次呼叫都疊一格 frame，而遞迴的每一層都在等下一層的結果、還沒 return，所以前面的格子一個都拿不掉，深幾層就同時佔幾格。迴圈從頭到尾只有一格，變數在同一格裡重複使用，跑 10 圈或 1 億圈 stack 用量都一樣。
  • 為什麼要分 .data 和 .bss？.data 的初值得存在執行檔裡；.bss 全是 0，執行檔只要記「需要多大」。全域宣告 int buf[1000000]; 不會讓 exe 大 4 MB。
  • 為什麼區域變數天生執行緒安全？每個 thread 有自己的 stack，區域變數各放各的。heap 上的物件、全域／static 變數才是大家共用的，多個 thread 同時改才要上鎖（I03）。
  • C# 的東西到底放哪？int、struct 當區域變數時整個值在 stack；class 物件一定在 heap，stack 上只放一個參考。static 欄位跟著型別活到程式結束。檔案 handle、GDI 這種 OS 資源不歸 GC 管，要 Dispose。
  • MCU 為什麼開機要先「複製 .data、清 .bss」？沒有 OS 也沒有虛擬記憶體，變數的初值只能燒在 Flash，RAM 掉電就空了。startup code 在進 main() 前把 .data 初值從 Flash 搬到 RAM、把 .bss 清 0；這段被改壞，全域變數初值就會亂掉。

C：每個變數在哪一區

int  g_count = 10;          // .data（有初值的全域）
int  g_buf[1024];           // .bss（沒初值，自動為 0）
const int MAX = 100;        // .rodata

void foo(int n)             // n：stack（參數）
{
    int  local = 3;         // stack（區域變數）
    static int calls = 0;   // .data（static 不在 stack，函式結束還在）
    char *msg = "hi";       // msg 指標在 stack，"hi" 本身在 .rodata
    int  *p = malloc(40);   // p 指標在 stack，那 40 bytes 在 heap
    calls++;
    free(p);                // 不 free 就是 memory leak
}                           // return：n、local、msg、p 這幾格全拿掉

int *bad(void)
{
    int x = 5;
    return &x;              // ✗ x 那格 return 就拿掉了，呼叫端拿到的是懸空位址（UB）
}

C#：值型別、參考型別與 OS 資源

void Run()
{
    int n = 5;                          // stack
    var pt = new Point(1, 2);           // struct：整個值在 stack
    var list = new List<int>();         // list 參考在 stack，List 物件在 heap（Gen0）
    var big = new byte[100_000];        // ≥ 85,000 bytes → LOH
    using var fs = File.OpenRead("a.txt");
                                        // FileStream 在 heap，檔案 handle 是 OS 資源 → using 負責關
}   // return：stack 那格拿掉；heap 上沒人參考的物件等 GC 收

I03多執行緒與同步

一句話：多個 thread 同時「讀－改－寫」同一份資料就會互相覆蓋（race condition）；用 lock 把那一段變成一次只能一個人進，但鎖拿的順序不一致就會互等到天荒地老（deadlock）。

L1是什麼

名詞意思
Race condition結果取決於 thread 執行的先後順序，每次跑可能不一樣（見主圖）
Critical section（臨界區段）存取共享資料、同一時間只能一個 thread 執行的程式碼段
Mutex／lock互斥鎖，同時只有一個持有者。C# 的 lock 是 Monitor 的語法糖，可重入（同一個 thread 可再進）；.NET 9 起建議用專用的 System.Threading.Lock 物件

L2為什麼

  • 為什麼 count++ 不安全？它在機器碼是 load、add、store 三步。任何兩步之間都可能被切走，或另一顆核心同時在做，於是兩個人都讀到舊值、各加 1、後寫的蓋掉先寫的（lost update）。單核心也會發生，因為隨時可能 context switch。
  • 怎麼破 deadlock？四個條件破一個就好，實務上最常破「循環等待」：全程式統一取鎖順序（例如依物件 ID 排序後依序拿）。輔助手段：用 Monitor.TryEnter(obj, 300) 設逾時、拿不到就放掉手上的鎖重來；鎖住的範圍內不要呼叫外部程式碼或事件（你不知道它會不會再去拿別的鎖）。
  • 為什麼需要 memory barrier？為了快，編譯器會重排指令、CPU 有 store buffer 會延後寫出。單 thread 看不出差異，但另一顆核心可能先看到「旗標＝完成」、後看到資料。x86 的排序規則較強（只有 store→load 會被重排），ARM 較弱，同一份無鎖程式在 ARM 上更容易出事。lock、Interlocked 都已內含屏障，自己寫無鎖程式才需要手動處理。
  • Lock、Interlocked、無鎖結構怎麼選？單一數值加減、交換 → Interlocked（一條帶 lock 前綴的指令）；多個欄位要一起改 → lock；佇列、字典 → 直接用 ConcurrentQueue、ConcurrentDictionary、Channel，不要自己發明。
  • 為什麼 lock(this)、lock(typeof(X)) 不好？外部程式碼也拿得到同一個物件來鎖，等於別人可以插手你的鎖，製造意料外的 deadlock。用一個 private 專用物件當鎖。
  • Priority inversion 怎麼解？優先權繼承：低優先權任務持有高優先權在等的鎖時，暫時提升到高優先權，先把鎖做完放掉；或優先權天花板：拿鎖時直接升到預設的高優先權。RTOS 的 mutex 通常有這個選項，semaphore 通常沒有。

I04計算機架構

一句話：CPU 算得很快，等記憶體很慢；cache 階層賭你「剛用過的還會用、旁邊的也會用」，pipeline 與 branch prediction 賭你「下一步會走哪」，賭錯的代價就是效能。

L1是什麼

名詞意思
Cache 階層L1（每核心、最小最快，指令與資料分開）→ L2（每核心，Zen 4 1 MB、Raptor Lake P-core 2 MB）→ L3（多核心共用，數十 MB）→ DRAM。量級見上圖
Cache linecache 搬資料的最小單位，常見 64 byte。讀一個 int，會把旁邊 60 byte 一起帶進來
命中率／AMAT平均存取時間 ＝ 命中時間 ＋ 未命中率 × 未命中代價。例：1 ns ＋ 5% × 100 ns ＝ 6 ns，未命中率 5% 就讓平均慢了 6 倍
Locality（區域性）時間區域性：剛用的很快會再用；空間區域性：用了這個，旁邊的也快要用到
未命中三種（3C）Compulsory（第一次碰，一定沒有）、Capacity（工作集比 cache 大）、Conflict（剛好映射到同一組，互相踢出）
Write-back／write-through寫入先只改 cache、被踢出時才寫回記憶體 vs 每次都同步寫到下一層
Cache coherence（MESI）多核心各有 cache，同一條 line 被一顆核心改寫時，其他核心的那份要作廢，保證大家看到一致的值
Pipeline把指令拆成幾個階段，像生產線一樣每個 cycle 推進一格，多條指令重疊執行
Hazard（危障）Structural：硬體資源不夠兩條同時用；Data：後一條要用前一條還沒算好的結果；Control：分支還沒算出來就要決定往哪取指令
Forwarding／stallForwarding：算好的結果直接從 EX／MEM 繞線送給下一條，不必等寫回；真的來不及就 stall（插 bubble）
Branch prediction分支結果出來前先猜一邊、先執行下去（speculative execution）；猜錯就沖掉重來，現代 x86 約 15～20 cycles
False sharing兩個核心各改各的變數，但兩個變數剛好在同一條 cache line，line 在核心間來回作廢搬移，效能大跌

L2為什麼

  • 為什麼不把 L1 做大一點？容量越大，查表線路越長、越慢。所以用多層：小而快的放最近，大而慢的在後面。L1 命中約 1 ns，DRAM 約 100 倍慢。
  • 為什麼二維陣列換個迴圈順序能快好幾倍？C 與 C# 的 int[,] 是逐列（row-major）連續存放；Java 與 C# 的 int[][] 是「陣列的陣列」，每一列各自連續、列與列之間不一定相鄰，結論一樣。內層迴圈跑列內，連續存取，一條 cache line 用滿 16 個 int；內層跑行，每次跳一整列，幾乎每次都未命中。
  • 為什麼 linked list 常比 array 慢？array 連續，硬體 prefetcher 猜得到下一個；list 節點散在 heap，每走一步都可能是一次 DRAM 存取（pointer chasing）。理論上同樣 O(n)，實際差很多。
  • 為什麼排序過的資料，同一個 if 迴圈跑比較快？排序後分支結果是「一長串 false 再一長串 true」，branch predictor 幾乎全猜中；亂序資料約一半猜錯，每次賠 15～20 cycles。對策：先排序、改成無分支寫法（查表、條件運算），或讓編譯器產生 cmov。
  • False sharing 為什麼會讓多執行緒反而變慢？MESI 以 line 為單位管理。核心 A 寫 counts[0]、核心 B 寫 counts[1]，在程式上毫無關係，但它們在同一條 64 B line，每次寫都要把對方那份作廢、再搬過來。對策：每個 thread 的資料隔開至少 64 B（padding、alignas(64)、C++17 std::hardware_destructive_interference_size、Java @Contended），或各自用區域變數累加，最後再合併。
  • Pipeline 越深越好嗎？越深每級越短、時脈拉得高，但分支猜錯要沖掉的指令越多、資料危障要等越久。這是時脈與 IPC 的取捨。

L2為什麼

  • 為什麼 cmd > f 2>&1 和 cmd 2>&1 > f 不一樣？重導由左到右執行，2>&1 的意思是「讓 2 指向 1 現在指的地方」。前者先把 1 指到檔案，再讓 2 跟過去，兩者都進檔；後者讓 2 先跟著 1 指到螢幕，之後才把 1 改到檔案，錯誤訊息還是在螢幕。
  • 為什麼 free 顯示可用記憶體很少，卻不是記憶體不足？Linux 會把空著的記憶體拿來當檔案快取（page cache），需要時隨時可以讓出。看 available 欄，不是 free 欄。
  • 為什麼 kill -9 是最後手段？SIGTERM（15）可以被程式攔下來做收尾：寫完檔案、關連線、刪暫存檔。SIGKILL（9）不能攔，直接結束，可能留下寫一半的檔案與鎖檔。D 狀態的行程連 -9 都要等 I/O 結束。
  • 為什麼 load 高不一定是 CPU 不夠？Linux 的 load 也算卡在 D 狀態等磁碟或 NFS 的 thread。load 很高但 top 的 CPU 閒著，wa（I/O wait）高，瓶頸是磁碟或網路儲存。
  • 為什麼 chmod 777 不能當解法？等於所有使用者都能改你的程式或腳本，任何一個帳號被入侵就能植入程式碼。只開需要的權限，或把使用者加進對應群組。

一句話：資料一層一層包起來送：應用層（HTTP）交給 TCP 切段、編號、確認重送，IP 負責找路，乙太網路負責送到下一站；TCP 開始傳之前先用三方交握確認雙方都能收能送。

L2為什麼

  • 為什麼 TCP 會「黏包」？TCP 只保證位元組順序正確，不保證你送一次、對方就收一次。送兩筆 100 B，對方可能一次收到 200 B，或先收 60 B 再收 140 B。所以自訂協定一定要有訊框：固定長度、長度前綴（前 4 byte 寫長度）或分隔字元（如 \n），接收端迴圈讀到湊滿為止。
  • 為什麼要 TIME_WAIT？主動關閉方送出最後一個 ACK 後，不確定對方收到沒有；萬一遺失，對方會重送 FIN，自己要還在才能回。也避免同樣四元組的新連線收到舊連線遲到的封包。
  • 為什麼即時影音、遊戲用 UDP？TCP 掉一個封包，後面所有資料都要等它重送到才交給程式（head-of-line blocking）。影音晚到的封包已經沒用，寧可丟掉繼續。
  • 為什麼 HTTP/3 要改走 UDP？HTTP/2 在一條 TCP 上多工很多請求，掉一個封包所有請求一起卡。QUIC 在 UDP 上自己做可靠傳輸，掉封包只影響那一條 stream；加上 TLS 合併進交握，建連線更快。
  • 為什麼小訊息一問一答會莫名延遲？Nagle 會等前一段的 ACK 回來才送下一小段，而對方的 delayed ACK 又想等一下再回 ACK，兩邊互等，每次多出數十到數百 ms。命令式協定（下命令、等回應）通常要開 NoDelay。

L2為什麼

  • Index 為什麼快、為什麼不能每欄都建？沒有索引就整表掃描，百萬列要讀百萬列；B+ tree 幾層就找到。但每次 INSERT／UPDATE 都要同步維護每一棵索引樹，還佔空間。只替常出現在 WHERE、JOIN、ORDER BY 的欄位建。
  • 為什麼明明有索引卻沒用到？欄位被函式包起來（WHERE YEAR(t) = 2026）、型別隱式轉換（字串欄位拿數字比）、LIKE '%abc' 開頭萬用字元、違反最左前綴、或資料庫判斷結果太多列、整表掃反而快。改寫成 t >= '2026-01-01' AND t < '2027-01-01' 就能走索引。
  • 隔離級別為什麼不一律開最高？越高的級別要鎖越多、越久，或要保留更多版本，併發量下降、deadlock 與重試變多。多數系統用 Read Committed，對真正要一致的那幾筆另外加鎖（SELECT … FOR UPDATE）或用樂觀鎖。
  • MVCC 是什麼？多版本：寫入時保留舊版本，讀取看自己交易開始（或語句開始）那一刻的快照。讀不擋寫、寫不擋讀，PostgreSQL、InnoDB 都這樣做。
  • 為什麼要正規化，又為什麼有時反正規化？同一件事存多份，就會有更新異常（改了一處忘了另一處）、插入異常（沒有訂單就存不了客戶）、刪除異常（刪最後一筆訂單連客戶資料也沒了）。但報表查詢要 JOIN 很多表時，會刻意保留冗餘欄位或另做彙總表換速度。
  • 為什麼一定要參數化查詢？字串拼接時，使用者輸入 ' OR '1'='1 就能改變 SQL 語意（SQL injection）。參數化讓值永遠只是值；附帶好處是執行計畫可重用。

這兩個差在哪
